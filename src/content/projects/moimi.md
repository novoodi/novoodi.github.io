## 풀려던 문제

모임 장소를 정하기 어려운 이유는 정보가 없어서가 아니라 **기준이 충돌하기 때문**입니다. 다섯 명이 모이면 취향이 다섯 갈래고, 개인 선호를 평균 내면 아무도 만족하지 않는 중간값이 나옵니다.

그래서 개인 취향은 여러 판단 기준 중 하나로 내려 두고, 가장 위에 **그날 모임의 목적**을 두었습니다. 같은 사람들이 같은 동네에서 만나도 목적이 다르면 답이 달라집니다.

| | 축하 자리 | 위로 자리 |
|---|---|---|
| 상황 판정 | `CELEBRATION` | `CONSOLATION` |
| 1순위 판단 기준 | 목적 적합 41.4% | 제약 준수 44.2% |
| 최종 1위 | 루프탑 다이닝 (0.879) | 골목 포차 (0.865) |

위 수치는 실제 구현의 실행 결과이고, 스냅샷 테스트가 재현해 고정합니다.

또 하나의 문제는 프라이버시입니다. 기존 AI 추천은 대화 원문을 그대로 클라우드에 보내야 합니다. 이 앱에서는 원문이 휴대폰을 떠나지 않습니다.

## 구조

```
[채팅 원문]
   │  상황 분류 (온디바이스)        → 경계를 넘는 것은 상황 라벨 하나
   │  Gemma 4 익명화 요약 (온디바이스)
   │  거름망: 고정 9슬롯 블록으로 정형화, "이번 주 토요일" → 절대 날짜
   │  PII 스크러버: 이름·전화·이메일 규칙 기반 마스킹
   ▼
───── 디바이스 경계 ─────  나가는 것: 정형화 블록 + 판단 기준 가중치
   ▼
Gemini (클라우드): 날씨·장소 검색 도구 호출 → 추천 생성
   ▼
검증: Guardrail(장소 실존 확인) + Reflection(싫어요 위반 자기비평)
   │  실패하면 피드백을 누적해 최대 3회 재시도
   ▼
AHP 종합 랭킹 → 화면 표시 → 모임 후 만족도가 다음 판단 기준으로 되먹임
```

## 내가 한 일

- **상황 인식 분류.** 채팅을 9개 모임 상황(식사, 술자리, 카페, 축하, 위로, 액티비티, 여행, 스터디, 일반)으로 판정합니다. 가중 키워드 투표에 부정 표현 억제를 더해, "술은 안 마셔"가 술자리 신호로 잡히지 않게 했습니다.
- **거름망(정형화 게이트).** 형식 없는 대화를 고정 9슬롯 블록으로 바꿉니다. 값이 없으면 키를 지우지 않고 "미정"으로 남기고, 상대 날짜는 여기서 절대 날짜로 환산합니다. 모델에게 날짜 계산을 맡기지 않기 위해서입니다.
- **AHP 다기준 의사결정.** 5개 기준(목적 적합, 취향 적합, 제약 준수, 검증 신뢰, 과거 만족)의 상황별 쌍대비교 행렬에서 가중치를 구하고, 일관성 비율(CR)로 유효성을 판정합니다. 후보 점수는 전부 결정론적으로 매깁니다. LLM에게 점수를 물으면 채점자가 곧 채점 대상이 되어 검증이 성립하지 않기 때문입니다.
- **자율 검증 하네스.** Guardrail이 추천 장소의 실존 여부를 외부 API로 확인하고, Reflection이 사용자가 싫다고 한 조건을 어겼는지 검사합니다. 검증할 수 없는 경우는 "검증됨"과 구분해 3가지 상태로 표기합니다.
- **피드백 순환.** 모임 후 5점 척도 만족도가 들어오면 원인별로 판단을 고칩니다. 가중치를 직접 고치지 않고 쌍대비교 판단을 고쳐서, 학습 결과도 다시 CR 검사를 받게 했습니다.
- **온디바이스 임베딩 검색.** EmbeddingGemma-300m을 LiteRT와 DJL 토크나이저로 직접 구동해, 지난 모임 후기를 기기 안에서 임베딩하고 검색합니다.
- **Constrained decoding.** 온디바이스 Gemma의 성향 압축 출력을 툴 스키마로 문법 제약해 깨진 JSON을 구조적으로 막았습니다.
- **API 키 서버 격리.** Gemini, 카카오 로컬, 기상청 호출을 Firebase Functions 프록시로 옮겨 앱(APK)에는 키가 없습니다.

## 한계

측정하지 않은 것을 성과로 말하지 않기 위해 적어 둡니다.

- 위 실기기 표는 **기반 파이프라인**(요약, 압축, 후기 검색, 추천)의 측정치입니다. 상황 분류, AHP, 거름망, 재학습은 JVM 테스트와 에뮬레이터까지가 근거이고 실기기 정량 평가는 아직 하지 않았습니다.
- 후기와 지표 데이터가 수백 건 규모라, "개인화 성능을 얼마나 높였다"고는 주장하지 않습니다.
- 상황 분류는 어휘 사전 기반이라 신조어와 은어에 약합니다.
- 후보 점수 루브릭의 척도가 기준마다 달라, "AHP로 최적해를 구했다"고 말하지 않습니다. 말할 수 있는 것은 상황이 정한 가중치로 후보를 일관되게 정렬했고 그 가중치의 일관성을 CR로 검증했다는 데까지입니다.

## 이 프로젝트에서 지킨 원칙

- 문서보다 코드 실측을 먼저 봅니다. 의존성 추가나 구조 변경은 본 구현 전에 작은 실험으로 통과·실패 기준을 정해 판정했습니다.
- 온디바이스 모델은 골든 테스트로 정확도를 보증합니다. 임계값에 못 미치면 완료로 보지 않았습니다.
- LLM 출력은 그대로 믿지 않습니다. 프롬프트 지시는 1차 방어일 뿐이고, 집행은 결정론적 검증 단계가 합니다.
- 이 시스템은 사용자가 버튼을 눌러야 동작하고 최종 결정은 사람이 하므로, 에이전트가 아니라 어시스턴트라고 부릅니다.
