## 풀려던 문제

휴대폰에는 카톡과 알림이 계속 쌓입니다. 그중에서 "나한테 묻는 말인가, 나한테 시키는 일인가, 광고인가, 오늘 봐야 하는가"를 판단하고 싶었습니다. 다만 다른 사람의 메시지가 들어 있으므로 **판단은 휴대폰 안에서만** 이뤄져야 했습니다.

## 진행 과정

1. **모델 고르기.** 추가 학습 없이 소형 모델 두 개를 같은 한국어 문항으로 비교했습니다. 둘 다 쓸 수 없는 수준이었습니다(35.5% 이하).
2. **한국어 학습.** Qwen3.5-0.8B 기반 모델에 LoRA와 분류 헤드를 붙여 3i4K 화행 데이터 1,200문장, 이어서 5,000문장으로 학습했습니다. 5,000문장의 개선 폭은 95% 신뢰구간이 −0.61 ~ +2.87%p라서 "확실한 개선"이라고 쓰지 않았습니다.
3. **ONNX 변환 실패.** 모델의 일부 연산이 ONNX로 풀리지 않아 그래프가 수만 노드로 불어났고 세션 생성에서 멈췄습니다. 이 시점의 결론은 "실행 불가"였습니다.
4. **llama.cpp로 우회.** 모델 본체는 llama.cpp에서 토큰별 은닉 벡터만 뽑고, 분류 헤드(행렬곱 2개)는 Kotlin에서 계산하도록 나눴습니다. PC에서 F32, Q8, Q6, Q4 양자화를 PyTorch와 비교해 Q6_K를 골랐습니다.
5. **실기기.** 직접 쓴 JNI 브리지를 arm64로 빌드하고, 앱 안의 일치 검사 화면에서 스레드 수별로 측정했습니다.
6. **메모리 줄이기.** 1.5GB의 원인이 "가중치 두 벌"(파일 매핑 원본과 CPU용 재배열 사본)임을 찾았습니다. 읽기 방식을 바꾸고 계산 버퍼를 512에서 128로 줄여 1.12GB로 낮췄습니다. 속도는 그대로입니다.
7. **알림·카톡용 재학습.** 합성 데이터 2,313줄로 다시 학습했습니다. 합성 검증셋에서는 좋아진 v2가 실제 폰 카톡에서는 오탐이 9건에서 16건으로 늘어난 것을 실제 데이터 평가로 잡았습니다. 원인(짧은 말을 전부 "예"로 가르친 보강 데이터)을 찾아 v3에서 고쳤습니다.

## 결과

| 항목 | 값 |
|---|---|
| 실기기 지연 (Galaxy Z Fold7, CPU 4스레드, Q6_K 647MB) | 질문 1개당 296ms |
| 실기기 판정 일치 (PyTorch 대비) | 64 / 64 |
| 실기기 메모리 (PSS) | 1.52GB → 1.12GB |
| 모델 로드 | 0.86초 |
| PC 전체 테스트셋 976문항 (Q6_K) | 95.18% (PyTorch 95.39%) |
| 한국어 학습 효과 (360문장, 두 판단 모두 정답) | 69.2% → 91.1% |

실기기 수치는 한국어 v2 모델 기준입니다. 지금 앱에 들어 있는 알림용 v3 모델은 PC 평가까지 했고, 실기기 일치 검사 결과는 아직 기록하지 않았습니다.

코드는 Kotlin과 C++ 약 5,100줄이고 JVM 단위 테스트가 71개입니다.

## 한계

- 실제 폰 평가셋은 정답 "예"가 19개뿐이라, 모델 간 1~2개 차이는 우연일 수 있습니다.
- 실제 카톡의 "답장 필요" 판정은 아직 약합니다(v3, 기준 0.8: 맞힘 13, 오탐 9, 놓침 6).
- arm64 전용이고 CPU만 씁니다.
- 실제 폰에서 뽑은 평가용 카톡과 알림은 다른 사람의 메시지라 저장소에 올리지 않았고, 점수만 문서에 남겼습니다.
